# PRD 0001: Sprout.ph API Documentation MCP Server

**Last updated:** Tuesday, Jul 29, 2026, 4:30 PM (UTC+8)

---

## Problem Statement

Internal developers building integrations against the Sprout.ph API (HR, Payroll, Ecosystem Integration) have no fast, queryable way to look up endpoint details. The official docs site at https://api-docs.sprout.ph/ is a JavaScript-rendered SPA that must be manually navigated — developers waste time searching through nested pages to find the right method, URL, required headers, and payload shape. No raw OpenAPI spec is publicly available from Sprout. An AI agent (Claude) cannot read the live docs site on its own because the site requires JavaScript execution to render.

---

## Solution

A read-only MCP (Model Context Protocol) server that gives AI agents structured, instant access to the full Sprout.ph API reference — without hitting the live docs site at runtime. The server:

1. Exposes a `list_library` tool — a table of contents that maps all available domain sections to their corresponding tools, so an agent always knows what to call
2. Exposes one reference tool per level-2 sidebar section of the Sprout docs (e.g. `get_hr_employees_ref`, `get_payroll_runs_ref`) — each tool returns the complete endpoint reference for that section from pre-scraped static JSON
3. Is populated by a one-time `npm run fetch-docs` scraper that uses Playwright to traverse the Sprout docs sidebar, extract all page content, and write structured JSON files per section

The server runs over SSE transport so the whole team can connect a single shared instance from their Claude clients.

## User Stories

### Discovery

1. As a developer, I want to call `list_library` and receive a complete table of contents, so that I know which domain tool to call without guessing
2. As a developer, I want the table of contents to show me domain groups (HR, Payroll, Ecosystem Integration) and their sections with tool names, so that I can navigate the API surface in one response
3. As an AI agent, I want `list_library` to return structured data with tool names and descriptions, so that I can select the correct reference tool without additional prompting
4. As a developer, I want the tool directory to be always in sync with the scraped data, so that tool names listed in `list_library` always exist as callable MCP tools

### API Reference Lookup

5. As a developer, I want to call a domain tool (e.g. `get_hr_employees_ref`) and receive all endpoints for that section, so that I can generate a correct API call without opening a browser
6. As a developer, I want each endpoint reference to include the HTTP method, full URL, required headers, query/path parameters, request body shape, and a response example, so that I have everything needed to write the integration code
7. As a developer, I want endpoint auth requirements (Bearer token, Ocp-Apim-Subscription-Key) to be clearly stated in each reference, so that I never forget auth headers
8. As an AI agent, I want each domain tool to return all endpoints for that section in a single response, so that I do not need to make multiple tool calls for one task
9. As a developer, I want reference data to include example request payloads, so that I can copy-paste and adapt rather than construct from scratch
10. As a developer, I want reference data to include example response payloads, so that I know what to expect and how to parse the result

### Scraper

11. As a developer, I want to run `npm run fetch-docs` once and have the scraper automatically discover all sections from the Sprout docs sidebar, so that I never need to manually define page mappings
12. As a developer, I want the scraper to expand all collapsible sidebar sections before extracting links, so that no sections are missed
13. As a developer, I want the scraper to wait for full network idle before extracting content from each page, so that dynamically loaded content is captured
14. As a developer, I want the scraper to print a validation report (pages scraped per section, total vs sidebar link count), so that I know immediately if any pages were missed
15. As a developer, I want the scraper to exit with a non-zero error code if the page count does not match the sidebar count, so that bad data never reaches the MCP server
16. As a developer, I want the scraper to write one JSON file per level-2 sidebar section under `src/data/`, so that the MCP server loads only the section it needs
17. As a developer, I want the scraper to automatically assign pages to sections based on their sidebar parent, so that section assignment is always correct without manual mapping
18. As a developer, I want re-running `npm run fetch-docs` to fully overwrite the existing data files, so that stale content is never served

### Scalability

19. As a developer, I want new Sprout docs sections to be picked up automatically on the next re-scrape with zero code changes, so that the MCP grows with the API without maintenance overhead
20. As a developer, I want each domain tool to only load its own section's data file, so that the MCP never loads all docs into memory at once
21. As a developer, I want the `list_library` table of contents to be generated from whatever section files exist in `src/data/`, so that it is always accurate after every scrape

### Server & Transport

22. As a developer, I want the MCP server to run over SSE transport, so that my whole team can connect from their Claude clients to a single shared instance
23. As a developer, I want to run the server locally with a single command, so that I can test it without any cloud setup
24. As a developer, I want to configure the SSE server port via an environment variable, so that I can avoid port conflicts on my machine
25. As a developer, I want the server to start and be ready to serve in under 5 seconds, so that restarts after a re-scrape are not disruptive
26. As a developer, I want no authentication required on the MCP server for v1, so that setup is as simple as possible

### Deployment Readiness

27. As a developer, I want the server to be deployable to Railway by adding a `railway.toml` or `Procfile`, so that the migration from local to cloud is minimal
28. As a developer, I want the server to read its port from the `PORT` environment variable, so that Railway's automatic port assignment works without config changes

## Implementation Decisions

### Runtime & SDK
- Node.js + TypeScript
- `@modelcontextprotocol/sdk` for MCP server and SSE transport
- `playwright` for the scraper (headless Chromium)

### Transport
- SSE (`StreamableHTTPServerTransport` from the MCP SDK). Exposes a single HTTP endpoint (default `/sse`) that MCP clients connect to. Port is read from `process.env.PORT` (default `3000`).

### Tool architecture — two levels

**`list_library`**
- Returns a JSON object: `{ groups: [{ label: string, sections: [{ toolName: string, description: string }] }] }`
- Generated at server startup by reading the filenames in `src/data/` and matching them to a metadata map written by the scraper (`src/data/_index.json`)
- Always accurate — if a file exists in `src/data/`, it appears in the TOC

**Domain reference tools**
- Named `get_{group}_{section}_ref` (e.g. `get_hr_employees_ref`, `get_payroll_runs_ref`)
- Take no arguments
- Load their corresponding `src/data/{group}_{section}.json` file on call and return its content as a formatted string
- Registered dynamically at server startup from the files found in `src/data/` — no hardcoded tool list

**`_index.json`** (written by scraper)
- Maps each data filename to human-readable label, group, section, and tool description
- Used by `list_library` at runtime and by the server's dynamic tool registration

### Scraper — `scripts/fetch-docs.ts`

Execution flow:
1. Launch Playwright (headless Chromium)
2. Navigate to `https://api-docs.sprout.ph/` — wait for network idle
3. Expand all collapsible sidebar sections (click all expand toggles, wait for stability)
4. Extract sidebar link tree: level-1 items = group labels, level-2 items = section names + URLs
5. For each level-2 section, navigate to each child page — wait for network idle — extract:
   - Endpoint method + URL
   - Description
   - Required headers (auth)
   - Path/query parameters (name, type, required, description)
   - Request body schema + example
   - Response schema + example
6. Write `src/data/{group}_{section}.json` (overwrites on re-run)
7. Write `src/data/_index.json` with TOC metadata
8. Print validation report: section → page count, sidebar link count vs scraped count
9. Exit 1 if any mismatch

### Data file format (`src/data/{group}_{section}.json`)
```jsonc
{
  "group": "hr",
  "section": "employees",
  "label": "Employees",
  "endpoints": [
    {
      "title": "Get Employee List",
      "method": "GET",
      "url": "https://api.sprout.ph/v2/hr/employees",
      "auth": {
        "headers": ["Authorization: Bearer {token}", "Ocp-Apim-Subscription-Key: {key}"]
      },
      "parameters": [
        { "name": "page", "in": "query", "type": "integer", "required": false, "description": "Page number" }
      ],
      "requestBody": null,
      "responseExample": { "data": [], "meta": {} }
    }
  ]
}
```

### Directory structure
```
sprout-mcp/
├── scripts/
│   └── fetch-docs.ts       # Playwright scraper
├── src/
│   ├── server.ts           # MCP SSE server entry point
│   ├── tools/
│   │   ├── list-library.ts # list_library tool
│   │   └── registry.ts     # dynamic tool registration from src/data/
│   └── data/               # generated by scraper — not committed to git
│       ├── _index.json
│       ├── hr_employees.json
│       ├── hr_leaves.json
│       └── ...
├── package.json
└── tsconfig.json
```

### `src/data/` in `.gitignore`
Scraped data is not committed — it is generated at setup time by running `npm run fetch-docs`. This keeps the repo lean and ensures data is always fresh from the live docs.

### Deployment
- Local: `npm run build && npm start`
- Railway: add `railway.toml` with `startCommand = "npm start"`. Server reads `PORT` from env.

## Testing Decisions

### What makes a good test
Tests verify **tool output shape and completeness** — not internal scraper implementation details. A good test checks that a tool returns the expected structure given a known data file, not how the scraper traverses the DOM.

### Test seams

1. **`list_library` unit test** — seed `src/data/_index.json` with fixture data, call the tool handler, assert the returned TOC matches the fixture. No network, no Playwright.

2. **Domain tool unit test** — seed a fixture `src/data/hr_employees.json`, call the `get_hr_employees_ref` tool handler, assert that endpoint method, URL, auth headers, and parameters are present in the output.

3. **Dynamic tool registration test** — given a set of fixture files in `src/data/`, assert that the server registers exactly those tools (plus `list_library`), no more, no fewer.

4. **Scraper integration test** (optional, slow) — run the scraper against the live Sprout docs, assert the validation report exits 0 and `_index.json` contains at least 3 groups. Gated behind a `CI_INTEGRATION` env flag — not run in standard CI.

### Prior art
No existing test suite in the repo (greenfield). Use `vitest` as the test runner (fast, TypeScript-native, no config overhead).

## Out of Scope

- Live Sprout API calls from within the MCP (the server is reference-only, not a proxy)
- Authentication on the MCP server (v1 is open; auth is a future concern for Railway deployment)
- Automatic/scheduled re-scraping (manual `npm run fetch-docs` only)
- A web UI or admin panel for the MCP server
- Support for other Sprout environments (staging, sandbox) — production docs only
- Rate limiting or connection caps on the SSE server
- Caching layer between the MCP server and `src/data/` files (files are small enough to read on each tool call)
- OpenAPI spec generation from the scraped data

## Further Notes

- The Sprout docs site is a JavaScript-rendered SPA — `axios` + `cheerio` alone cannot scrape it. Playwright (headless Chromium) is required.
- Auth headers confirmed from the docs: `Authorization: Bearer {token}` and `Ocp-Apim-Subscription-Key: {key}`. HR tokens expire in 1 hour; client tokens in 15 minutes. These details must be captured in each endpoint's reference.
- The sidebar depth of the live Sprout docs is unknown until first scrape. If any level-2 section contains more than ~30 endpoints, consider splitting it to level-3 tools in a follow-up engagement.
- `src/data/` must be in `.gitignore` — scraped data should not be committed.
- The MCP SDK's SSE transport is `StreamableHTTPServerTransport` (not the deprecated `SSEServerTransport`).
