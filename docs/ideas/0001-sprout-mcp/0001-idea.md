# Idea 0001: Sprout.ph API Documentation MCP Server

**Last updated:** Tuesday, Jul 29, 2026, 4:00 PM (UTC+8)

## Problem

Internal developers integrating with the Sprout.ph API (HR, Payroll, Ecosystem Integration) currently have to manually search the docs site at https://api-docs.sprout.ph/ to find the right endpoint, parameters, headers, and payload structure. The docs site is a JavaScript-rendered SPA with a large number of pages across nested sections — it is slow to navigate manually and not queryable by an AI agent.

There is no raw OpenAPI/Swagger spec publicly accessible. The only way to consume the docs programmatically is via a Playwright-based scraper that traverses the sidebar navigation.

## Target Users

Internal developers who use Claude (or any MCP-compatible AI agent) and need to look up Sprout.ph API reference while building integrations.

## Constraints

- No raw OpenAPI spec available from Sprout — must scrape the SPA docs site
- Read-only static reference library — no live Sprout API calls from within the MCP
- No internal sub-agents within the MCP server
- No authentication on the MCP server (local-first, Railway later)
- Transport: SSE (shared server the whole team connects to)
- Runtime: Node.js + TypeScript + `@modelcontextprotocol/sdk`

## Architecture Decisions

### Tool structure — two levels

**`list_library` (directory tool)**
Returns the full table of contents: all domain groups (level 1 sidebar) and their sections (level 2 sidebar) with tool names and descriptions. The agent calls this when it does not know which domain tool to use.

**One tool per level-2 sidebar section (domain tools)**
Examples: `get_hr_employees_ref`, `get_hr_leaves_ref`, `get_payroll_runs_ref`, `get_ecosystem_webhooks_ref`. Each tool takes no arguments and returns the full endpoint reference for that section (method, URL, parameters, headers, request/response examples) from a pre-scraped static JSON file.

The final tool list is discovered at scrape time — not hardcoded. New sidebar sections auto-generate new tools on the next `npm run fetch-docs`.

### Scraper — Playwright, sidebar-driven, fully automatic

- Input: root URL `https://api-docs.sprout.ph/`
- Playwright opens the page, expands all collapsible sidebar sections, waits for network idle
- Level 1 sidebar items → group labels in `list_library`
- Level 2 sidebar items → one MCP tool each + one JSON file in `src/data/`
- Pages under level 2 → content inside that section's JSON file
- Validation report printed after every scrape (pages scraped per section, total vs sidebar count)
- If count mismatch → script exits with error before bad data reaches the MCP

No manual page mapping ever needed. The sidebar is the single source of truth for domain assignment.

### Refresh cadence

Manual: `npm run fetch-docs`. Developer runs it when Sprout updates their docs. Server restarts to pick up new `src/data/` files.

### Deployment

- **Now:** Local (developer runs `node dist/server.js`, clients connect via SSE)
- **Later:** Railway (single persistent process, team points Claude clients at the Railway URL)

## Success Criteria

1. `list_library` returns an accurate, complete table of contents that lets the agent identify the right domain tool without guessing
2. Each domain tool returns enough structured content for the agent to generate a correct API call (method, URL, auth headers, parameters, example payload)
3. `npm run fetch-docs` completes without errors and the validation report shows no missed pages
4. Zero missed sections from the Sprout docs sidebar after one manual verification pass
5. Adding a new Sprout docs section requires zero code changes — only a re-scrape

## Open Questions

- What is the exact sidebar depth of the Sprout docs? (determines whether level-2 sections are granular enough or need a level-3 split — to be discovered on first scrape)
- Does Sprout use client-side routing that requires Playwright `waitForNavigation` between pages, or does each page load independently?
